# 问题分析类文档整理

适用于故障说明、问题定位、根因分析和排查指南。按读者的“发生什么、为什么、怎么确认、怎么处置”组织，同时保留来源和证据的确定程度。重组正文前，确认本次请求允许结构调整；仅要求格式调整时，先给重组建议，不擅自改章节。

## 一、参考骨架，不强制填满

以下六个栏目可以按已有材料合并、调整顺序或省略。即使缺少根因或解决方案，也可以交付清楚标注缺口的分析文档，不为凑章节编造内容。

- **当前结论与适用范围**：已确认了什么；适用对象、版本、环境和条件。没有确认根因时直接写“根因未确认”，恢复能力未知时写“尚未验证”，不要先给确定性承诺。
- **现象与影响**：报错原文、观测结果、时间、对象、范围；保留观察事实，不因暂时解释不了就删除。
- **原因或待验证假设**：有证据的因果链、证据来源和不足；多个原因或并行路径按实际关系表达。
- **判断与自查**：用于区分候选问题的证据、必要条件、排除条件、检查方法及判断盲区。
- **处置与验证**：先保全证据和检查恢复状态，再区分已执行动作、待执行建议、风险和复核方法。
- **预防与后续**：与已确认原因或有依据的风险对应、可落地的改进措施；未确认的措施标明验证前提，不为填满章节增加通用建议。

案例证据、完整日志、关联但独立的问题可放附录；关联是否独立需要来源支持，不能因为表现不同就直接拆成另一故障。

## 二、先区分事实、推测与建议

- **事实**：原文或用户提供的观测、命令输出、已执行动作；记录来源位置及对象/时间，不把它外推为所有环境事实。
- **假设**：解释现象的一种可能，写明支持与反对证据、尚未验证的条件；不能在排版时升级成“已确认根因”。
- **建议**：尚未执行的排查或处置；不得写成已执行成功，不编造执行结果。
- **待确认**：缺失的版本、数值冲突、统计口径不明、来源无法核实等，集中进入交付报告；正文确有必要引用时也保留“不确定”的限定。

来源不够时，可以只整理现象、已有排查和下一步需要什么证据，不能自行生成真实事故结论。

## 三、各部分的写法

### 结论与适用范围

可以先给简洁结论，也可以先说明已知事实与未决项，不强制第一句写明原因和恢复能力。环境、版本、开关状态等只按已有材料记录；“是否单副本”等存储案例特有条件，不自动套用到所有问题。

为了独立检索，可以在授权范围内从原文已有信息补齐主题，例如“某组件启动失败：现象与检查方法”。不要只写“见上一节”，也不必复制整篇背景到每块。

### 现象与影响

保留报错原文与观测范围，区分“典型表现”“本次观测”和“可能影响”。同一指标出现不同数值，先核对时间、对象、单位、权限、过滤和统计口径，不能自行选择较符合推断的值。

现象暂时无法被原因解释时，保留它并标注证据缺口。不要从“元数据完整”“文件数变化”等术语直接推断普遍互斥，也不要为了让叙述自洽删掉不吻合的观察。

### 原因与机制

可以按“结论—证据—机制”或真实时序展开。确有反常现象时解释它；没有矛盾不制造矛盾。

- 时序按来源描述，缺少时间点就不补造时间；并行原因保持并行，不改成两个有先后关系的事件。
- 区分触发条件、直接原因、背景风险和放大因素；只有证据支持时才称为因果关系。
- 只解释与当前问题相关且有依据的机制。应答、持久化、复制等只在对应系统和案例中说明，不作为所有问题的固定问题清单。
- 时序图或关系图仅辅助呈现已有事实；图中同样保留不确定性，不能用画图补出不存在的机制。

### 判断与自查

按证据用途分类，而不是按“配置/非配置”一刀切。

- 直接观测、日志特征、状态与来源支持的版本/配置组合，都可能是诊断依据或适用条件。
- 仅有风险配置，不足以证明本次问题已经发生；需要说明还缺哪些观测或排除条件。
- 已知缺陷与特定版本/配置相关时，保留该条件及来源，不因其是“静态配置”就删除。
- 有多少可靠依据就写多少，不强凑三到五条；没有可验证命令就描述需要何种证据，不编造命令。

### 处置与验证

按实际情况保留以下顺序约束，步骤缺少依据时标注待确认：

1. 保全日志、输出、对象标识及必要备份；说明采集的权限、敏感信息风险，不公开完整生产日志。
2. 确认系统是否正在恢复、有无正在执行的其他动作，避免建议相互干扰。
3. 分开列出“原文已执行”与“建议执行”，保留命令、参数、条件和风险。危险操作需要用户另行授权，本 Skill 只整理文字，不执行。
4. 记录验证方法和预期证据；原文未提供预期值时不自造阈值，不宣称已恢复。
5. 写明回退或不可恢复部分的处理边界；不知道恢复能力就保留未知，不承诺一定能恢复。

命令的语义依赖产品与版本，必须有可靠来源。照片中的 `fsck -delete` 等只是特定存储场景示例，不能据此给通用 `fsck` 或其他实现定义固定行为。

### 预防与后续

每项写清“对应原因/风险 → 动作 → 生效前提与代价 → 如何验证”。措施必须符合当前系统能力、权限和生产约束；单机/副本、持久化开关等示例不跨系统照搬。

原因尚未确认时，可以列“待验证的风险缓解建议”，但不能包装成已证明能预防复发的措施。纯粹凑数、没有对应依据的建议不加入正文。

## 四、完成后人工核对

- 原有观察、报错、命令、数字、条件及否定词是否保留？若删除重复材料，是否可追溯到来源？
- 已确认、推测、未验证的建议是否仍然区分？是否不慎把并行关系改成先后关系？
- 一个块单独取出时，是否能识别对象、适用前提和确定程度？长块拆分是否丢失警告？
- 修改摘要是否说明结构变化和来源对应？未决项是否单列？
- 是否实际进行了知识库预览与检索？没有做就写“未验证”，不把本地格式检查当成事故结论或召回效果验证。
