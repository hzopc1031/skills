# 故障分析类文档

读者会以问句检索（为什么丢、怎么确认、怎么修、怎么防），所以按**问句**组织，而不是按分析报告的顺序组织。

## 骨架

六章 + 两个可选附录，顺序不可调换。

| 章 | 是否必备 | 只回答一件事 |
| --- | --- | --- |
| 一、结论与适用前提 | 必备 | 是什么、在什么条件下成立 |
| 二、现象 | 必备 | 看得到什么：报错、表现、影响范围 |
| 三、根因 | 必备 | 为什么会发生：时序与因果链 |
| 四、判断与自查 | 可选 | 怎么确认是这个问题：判据、命令 |
| 五、解决方案 | 必备 | 怎么修、修不了怎么办 |
| 六、预防 | 可选 | 怎么不再发生，且必须可落地 |
| 附录一、案例数据 | 可选 | 实例证据，按「证据 1、证据 2」编号 |
| 附录二、关联问题 | 可选 | 另一个独立问题，别塞进正文 |

短文档可合并（判断并入现象、预防并入解决方案），但「结论 / 现象 / 根因 / 解决方案」四章必须在。

## 每章写什么

### 结论与适用前提

- 第一句就是结论：一句话说清「什么原因导致什么结果、能否恢复」。
- 第二段写适用前提：环境、版本、配置、是否单副本——决定结论对读者是否成立。
- 可加一行排查顺序，但不要写「见 §X」这类章节指针，用「先按判断与自查确认，再按解决方案处置」的表述。

### 现象

- 只写观察结果：典型现象（报错原文、命令输出特征）、本案例现象（对象、时间、数量）、影响（范围、是否可恢复、发现滞后多久）。
- 不写判据、不写操作清单、不写另一个问题的表现。
- 每条现象都要能被根因解释。反例：写「文件数量变少」，但根因说「元数据完整」——元数据在，文件条目就在，不会变少。
- 关联问题的表现不要混入，例如坏 meta 导致的 `.inprogress` 堆积属于另一个问题。

### 根因

- 开头先写**现象里的矛盾点**，再给结论，再按时序展开，避免一上来就抛结论。
- 第一段：现象中反常之处 → 推论 → 归因方向。
- 主体：按时间点编号，一条一件事，格式为「时间 + 发生了什么 + 结果」。不要用 `###` 小标题，也不要用「两条路径并行」「恶化条件」这类标签；一件事有两条并行路径，就分成两个时间点各写一条。
- 机制要写清「谁应答、应答前做了什么持久化动作」，读者才能判断窗口在哪。
- 时序图放末尾作为全貌，不在中间打断阅读。
- 不写监控建议、发现滞后——那些属于判断与预防。

### 判断与自查

- 只放能判定「是不是这个问题」的依据，三到五条：判据、排除项、判断盲区。
- 不该放这里的：静态配置项（是否开启某个开关）、容量余量、副本数、电源冗余、性能指标。这些是**风险因素**，只说明「有没有同样的隐患」，不能说明「这次是不是发生了」；放进根因（作为条件）或预防（作为改进项）。

### 解决方案

1. 先留证据（导出输出、日志、标识对照）——破坏性命令执行后现场不可复现；
2. 确认是否仍在自动恢复（还在恢复就别删）；
3. 执行动作，并写清命令的真实语义（例如 `fsck -delete` 只删元数据条目，不回收数据、不修复块）；
4. 复核判据（输出应变成什么）；
5. 不可恢复的部分怎么收尾（通知上游重跑、按分区重跑）。

最后写恢复边界：哪些情况无法恢复，别让读者以为「元数据在就等于数据可读」。

### 预防

- 每一条都必须可落地，并逐条对应前面写过的原因或问题；对不上的一律不写。
- 落地三问：生产真的会执行吗（性能代价可接受？）；现有形态支持吗（单 DataNode 提副本到 3 做不到）；有没有对应原因（存储隔离、journal、core dump 这类无证据的通用建议不要凑数）。
- 推荐三列列表：`- **对应原因 → 动作：** 说明（代价、阈值、是否已具备）`。

### 附录

- 案例数据：按「证据 1、证据 2」编号，每条一句加粗引导 + 列表；声明「仅作佐证，不代表读者环境实测结果」。
- 关联问题：另一个独立故障，写清现象、定位、处理，不与主线混写。

## 反例

| 反例 | 为什么错 |
| --- | --- |
| 现象里写「文件数变少」但根因说「元数据完整」 | 两者互斥，读者会立刻发现矛盾 |
| 把关联问题的现象混进本案例现象 | 现象与根因对不上，回答时会答偏 |
| 根因第一句直接给结论 | 没有从现象过渡，读者不知道结论从哪来 |
| 用「两条路径并行」「恶化条件」当小标题 | 标签化表述读起来像提纲，不如按时间点平铺 |
| 判断章列「是否开启某配置」「内存余量」「副本数」 | 这些是风险因素，不是判据 |
| 解决方案直接从删文件开始 | 没留证据、没确认是否仍在恢复 |
| 预防写「开启每包 fsync」「单机提副本到 3」 | 生产不会执行，或物理上做不到 |
